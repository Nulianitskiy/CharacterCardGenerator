# План фичи: «Объекты» (предметные карточки)

Сущность для создания **физических двусторонних карточек предметов**: склеенные
«рубашка» + «описание» — как на референсах `.vscode/Шмотки + баффы*.pdf`, но
распечатываемые одним листом, где рубашка и описание объекта стоят **рядом**
(пара за парой), без линии сгиба — пару предполагается вырезать и склеить.

## 1. Что показал референс

**Сторона «рубашка»** (файл `Шмотки + баффы.pdf`):
- багровая (тёмно-красная) карточка со скруглёнными углами;
- сверху имя предмета белым серифным по багровому;
- в центре светлое «окно» с изображением предмета;
- снизу свиток-роспись со **слоганом**;
- в правом верхнем углу круглый **бейдж количества** (число: 2, 3, 4, 5…).

**Сторона «описание»** (файл `Шмотки + баффы рубаха.pdf`):
- та же багровая подложка;
- светлая плашка с именем сверху;
- подпись «Описание»;
- большая светлая рамка-коробка с **выключенным (justified) текстом** описания.

Сетка в референсе: 3×3 карточки на A4, рубашки и описания — на **разных листах**
(главная боль: их надо совмещать при склейке). Новая фича решает это соседством
пар на одном листе.

## 2. Модель данных (новый entity)

```ts
export interface GameObject {
  id: string;
  file: File;               // картинка для рубашки (пока обязательна, как у карточек)
  imageUrl: string;         // blob URL — живёт по тем же правилам revoke
  name: string;             // имя: рендерится на обеих сторонах
  slogan: string;           // текст на свитке рубашки; пустой → свиток не рисуется
  description: string;      // текст в рамке описания
  quantity: number | null;  // бейдж «n штук» на рубашке (null — без бейджа)
  theme: ObjectTheme;       // палитра: 'ruby' | 'emerald' | 'obsidian'
}

export type ObjectTheme = 'ruby' | 'emerald' | 'obsidian';
```

Объект — **отдельная сущность**, а не `CharacterCard` + поля:
у него другой набор опций, другой PDF-рендер, и mixing с инициативками только
загрязнил бы `CharacterCard`. Общие механики переиспользуем через примитивы:
`imageIngest` (файл → объект, свои строки ошибок), `FilledCharacterImage`,
`FittedName`/`nameLabelRender` (плашка имени), `layoutImageFill` (окно картинки).

## 3. Геометрия листа (constants.ts — единственный источник правды)

Карточка ≈ 66.7 × 95.7 мм (как в референсе, близко к M:TG 63×88, ratio 0.7).

Лист «Объекты», вариант по умолчанию **«9 ячеек 3×3, объект = две соседние ячейки»**:

```
[рубашка₁][опис₁][рубашка₂]
[опис₂][рубашка₃][опис₃]
[рубашка₄][опис₄][ пусто ]
```

- строка-мейджор: рубашка сразу за ней её описание → пара режется одним движением,
  склейка без угадывания;
- 4 объекта на лист + одна свободная ячейка (в ней не рисуем ничего — просто
  поля листа; можно печатать «запасные рубашки» отдельным листом позже);
- порядок объектов = порядок в списке (drag-reorder сохраняется);
- линии реза: белая сетка ячеек (механизм `gridCutSegments` уже есть и покрыт тестами),
  **без** пунктирных сгибов.

Альтернативы, которые сознательно **отложены**: 2×2 листа (крупные карты),
«рубашки отдельным листом» (как в референсе — проигрывает по UX совмещения).

Внутренние доли карточки (в долях высоты/ширины карточки, все — в `constants.ts`):
- рубашка: имя ≈ 12% сверху, окно картинки ≈ 62%, свиток ≈ 18%, бейдж — круг Ø≈16% в углу;
- описание: плашка имени ≈ 14%, подпись ≈ 6%, рамка текста ≈ 76%.

## 4. Текстовый движок (главная новая мат часть)

Описания длинные (см. референс) → нужен **перенос строк + выравнивание по ширине**:
- новый чистый модуль `src/utils/justifiedText.ts`: вход — текст, box (w,h),
  `measure(line) => width` (callback!), выход — раскладка строк с межсловными
  разрывами + сигнал `overflow` (не влезает при минимальном кегле);
- тесты на fake-measure (ширина = длина·k) — без DOM;
- PDF: вызов с canvas-measure, рисование по словам со сдвигом;
- экран: CSS `text-align: justify` + тот же алгоритм не нужен — но **кегл
  подобран так, чтобы экран и PDF совпадали** (тот же scale, что у имени).
- при переполнении — warning в UI («описание не влезает, сократите») и в PDF
  текст обрезается по рамке, не залезая на имя.

## 5. Архитектура UI (два рендерера, одна геометрия)

- **Переключатель режима**: третья кнопка в шапке — «Инициативки / Павны / Объекты».
  Режим листается как режим печати; состояние объектов — отдельный массив
  `objects: GameObject[]` в App (со своим beforeunload/очисткой).
- **Сетка предпросмотра**: новый `ObjectGrid` (обёртка над grid-раскладкой) +
  `ObjectCard` c двумя «фишками» пары; тайл smaller-grid не переиспользуем —
  у объекта 2 лица разной природы. Drag-reorder пар — как в CardGrid.
- **Панель опций объекта**: секции «Имя + слоган», «Описание», «Картинка»
  (crop-фокус переиспользуется), «Количество». По образцу `cardOptions/*`.
- **PDF**: новый `src/utils/objectPdfRender.ts` — рисует рубашку и сторону
  описания на canvas по мм-геометрии из constants; `pdfGenerator.ts` получает
  ветку `mode === 'objects'`, имя файла `objects-<date>.pdf`.
  Скруглённые плашки/свиток — примитивы canvas (roundRect, эллипс свитка,
  «бахрома» как в DnD-панели), без новых изображений-ассетов.

## 6. Этапы

1. **Чистая математика** (TDD): геометрия листа и карточек в `constants.ts`
   (`getGameObjectSize`, packing пар в сетку — новый `src/utils/objectLayout.ts`),
   justified-раскладка — модуль + тесты.
2. **PDF-рендер**: рубашка и описание на canvas, ветка режима в generatePDF.
   Проверка: смоук с генерацией PDF на 4–5 объектах, глазами + `pdfLayout`-подход.
3. **Экран**: режим «Объекты», ObjectGrid/ObjectCard, загрузка файлов,
   drag-reorder, панель опций, live-превью пар.
4. **Интеграция и полировка**: персы строки/порядка → в проект JSON (см. ROADMAP п.3),
   README/AGENTS, smoke E2E (upload → PDF в обеих раскладках не сломалась).

## 7. Решения

**Принято:**
- **Бейдж количества** — в v1, опциональный (число или пусто).
- **Пустой слоган** — свиток не рисуется, окно картинки занимает всё доступное место.
- **Палитры** — в v1 сразу 2–3 темы (`ruby` как референс, `emerald`, `obsidian`).
  Палитра — данные в `constants.ts` (`OBJECT_PALETTES: Record<ObjectTheme, {...}>`:
  фон карточки, светлая плашка, чернила, акцент бейджа, цвет свитка), откуда её
  читают и CSS-переменные экрана, и canvas-PDF — снова «one geometry, two renderers».
  Выбор темы — в панели опций объекта (на v1 — одна тема на весь лист или
  на объект? Предлагаю **на объект**, как в карточках с пресетами).

**Осталось подтвердить (пока беру рекомендованное):**
1. **Плотность**: 3×3 по 9 карточек → **4 объекта/лист** *(взято по умолчанию)*,
   или 2×2 → 2 крупных объекта/лист?
2. **Порядок пары**: **рубашка слева, описание справа** *(взято по умолчанию)*,
   или наоборот?

## 8. Риски

- Justified-текст на canvas — самая коварная часть; на экране и в PDF строки могут
  разойтись (другие шрифты в fallback). Митигация: тот же ensureNameFontsLoaded
  и один measure-pipeline; расхождение не критично для печати, но preview
  обязан предупреждать о переполнении тем же сигналом, что PDF.
- Blob-URL-гигиена для `objects` — дублируем паттерн `cards` (утечки уже лечили).
- Третья раскладка тронет переключатель режима в App/CardGrid — аккуратно,
  чтобы 4/20-поведение не изменилось (тесты pdfLayout/pawnLayout — страховка).
